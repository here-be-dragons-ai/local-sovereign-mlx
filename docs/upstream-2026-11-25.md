## Commits on our path (v0.8.0 -> v0.8.1)

- **`#2806` prompt admission** (betizzel): `PromptProcessingBatch.prompt_step`
  kept the step's lazy `output` and `logits` alive while the prompt cache was
  evaluated and handed to the APC coordinator. Their unused graphs referenced
  the previous step's KV and recurrent buffers, so under a tight budget the
  checkpoint was refused for headroom that was about to be free, and the
  prefix was silently not cached. Three lines in `generate/ar.py`; found
  serving Qwen3.8-27B with APC on an M5 Pro with 48 GB, i.e. this machine.
  No hunk overlap with `0010`, which sits in the batch generator's `generate`
  loop 240 lines below.
- **`#2753` one generation stream**: `generate_step` and `stream_generate`
  run every iterator step on one thread-local stream, which
  `speculative/common.py` now shares (before: a second stream object of its
  own). The server's batch engine uses neither entry point; only the drafter
  calls in `speculative/mtp.py` change stream. Motivation was a stall in
  distributed generation.
- **`#2747` thinking default**: `get_chat_template` no longer injects
  `enable_thinking=False` when the caller gives nothing. **Server unaffected**:
  `GenerationArgs.to_template_kwargs` always sends a bool (server default
  off, `MLX_VLM_ENABLE_THINKING`). The change reaches only the CLI
  `mlx_vlm.generate`. `thinking_mode` is now `"disabled"` instead of absent
  when a template references it and thinking is off; none of our templates
  does (Qwen3.8 and Kolibri read `reasoning_effort`, Apertus
  `enable_thinking`).
- **Tool calls in the server** (`#2784`, `#2786`, `#2817`): text beside a tool
  call survives non-streaming responses; a response-template tool call the
  template cannot decode (truncated by `max_tokens`, malformed JSON, missing
  `args`) no longer ends the turn with an error event or raw control tokens
  in `content`; failed tool calls are reported the same way on
  `/v1/chat/completions`, `/v1/responses` and `/v1/messages`. 222 lines in
  `server/openai.py`, 72 in `server/responses_state.py`; the `apertus` parser
  is untouched. Checked below with a text request and a tool call.
- **`#2771` APC image hash**: list-valued `pixel_values` hashed to 0, so
  different images shared one cache. Images only.
- **`#2752` SenseNova-Loop**: `qwen3_5/language.py` gains an
  `execution_layers` property and iterates over it; for Qwen3.8 the property
  returns `self.layers`, so the forward is unchanged (greedy hash below).
- **`#2795` attention-sink cache** (`models/cache.py`, +141 lines, new class)
  and `#2760` video timing in the APC request key (one line in
  `server/generation.py`): neither reaches a text request.
- `#2765` `apply_min_p(min_p=0)` returns instead of raising;
  `#2767` `resize_image` rejects non-positive targets; `#2778` Inkling 2 Mini
  reads native quantisation metadata in `utils.py`, only for ModelOpt
  checkpoints (`quant_method == "modelopt"`); ours carry `quantization` and
  skip the branch.
- Not on our path: Granite Docling, Depth Pro 2, Inkling 2 Mini kernels,
  DeepSeek V4 tool calling, Muse Glimmer, MiniCPM-OCR-Jev, qwen2_5_vl video
  RoPE, trainer removal and the training CLI, MathVista eval.

`test_server`, `test_gated_delta`, `test_tool_streaming`, `test_processors`
(test venv in the worktree, `-e ".[test]"`, `mlx 0.32.4`, `transformers

production server (5.15.1) never takes that path; the `apertus` tool parser
is a different mechanism (checked below). Not our patches: same counts
without them. `test_models -k apertus`: 11 passed in all three runs. The 13
`embedding_gemma2` failures of 11-16 were a `transformers 5.23` artefact and
do not appear with 5.15.1. The suites grew from 4576 to 4986 cases with
0.8.1.
